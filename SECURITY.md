# Кибербезопасность и защита данных

Прототип **«Фотопринт · AI-ассистент руководителя»**, хакатон Track 3.

> Честная рамка: это демо-прототип, а не промышленная система. Ниже разделены
> **реализованные меры**, **проверки** и **ограничения**, которые нельзя скрывать.
> Для реальных ПДн нужны доработки из раздела «Что сделать до продакшна».

---

## 1. Коротко для слайда

- **Роль определяет сервер, а не браузер.** Подписанная HttpOnly-cookie, роль и ACL
  перечитываются из БД на каждом запросе.
- **RBAC + ACL на уровне документов и папок.** Чужой финансовый документ даёт `403`
  и запись в аудите, а не «пустой ответ».
- **ПДн маскируются до внешней LLM.** ФИО, телефоны, email, IBAN, карты, УНП, паспорта,
  организации заменяются тегами; сырые значения возвращаются только в памяти запроса.
- **Аудио не уходит в облако.** Запись встречи расшифровывает локальный Vosk; временные
  аудиофайлы удаляются после распознавания.
- **Каждое значимое действие попадает в аудит.** Директор видит всё, сотрудник — только
  свои записи; в аудите нет сырых ПДн.
- **Секреты не в коде и не в архиве.** `.env` в `.gitignore`, в ZIP для другого компьютера
  ключи и база не попадают.

## 2. От чего защищаемся

| Угроза | Что может произойти | Мера в прототипе |
|---|---|---|
| Доступ сотрудника к чужим данным | Финансы, HR, чужие встречи и задачи | RBAC + ACL на сервере, фильтрация до ранжирования, `403` + аудит |
| IDOR | Подстановка чужого `event_id` / `task_id` / `doc_id` | Проверка владельца и роли на каждом объектном эндпоинте |
| Утечка ПДн во внешнюю LLM | ФИО/телефоны/email уходят провайдеру | Маскирование, `assert_clean`, маскированный preview, аудит без сырых ПДн |
| Prompt injection из документа | Документ просит модель «забыть правила» | Системный промпт + обёртка `<documents>`, инструкции внутри — данные |
| Кража/подделка сессии | Клиент меняет роль или `user_id` | Подписанная cookie, роль из БД, `HttpOnly`, `SameSite=Lax`, TTL 8 ч |
| Перебор/спам AI | Сжигание токенов и деградация сервиса | Лимит 20 запросов/мин на пользователя и действие, `429` + `Retry-After` |
| Огромные/битые файлы | DoS парсера, переполнение контекста | Лимит 2 МБ, 200 тыс. символов, только разрешённые форматы |
| Утечка секретов | Ключ DeepSeek или `SECRET_KEY` в git/архиве | `.env` в `.gitignore`, `.env.example`, ZIP без секретов, ротация ключей |
| Компрометация публичной ссылки | Любой с ссылкой видит демо | Осознанное ограничение демо; для продакшна — SSO и код доступа |

## 3. Что реализовано

### 3.1. Аутентификация и сессия

- Сессия — подписанный токен `itsdangerous.URLSafeTimedSerializer` в cookie `fp_session`.
- Cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`, TTL 8 часов; флаг `Secure`
  включается через `COOKIE_SECURE=1` при работе по HTTPS.
- В токене только `uid` и необязательный `act_as`. Роль, ACL, имя и отдел **не берутся
  из клиента** — они перечитываются из БД на каждом запросе.
- Просмотр «как сотрудник»:
  - доступен только директору (`_real_role == "boss"`);
  - переключиться можно только на сотрудника;
  - факт переключения и возврата пишется в аудит (`role.switch`);
  - сотрудник не может переключиться обратно.
- Просроченная или подделанная подпись → `401`, а не «доверяем тому, что прислали».

### 3.2. RBAC и ACL

- Две роли: **директор** (`boss`) и **сотрудник** (`employee`).
- ACL документов и папок: `all`, `fin`, `hr`, `prod`, `mkt`, `support`, `legal`.
- Проверка прав — **на сервере**:
  - список документов уже отфильтрован по ACL пользователя;
  - поиск и ранжирование идут только по доступным документам;
  - явный запрос закрытого документа → `403` + `assistant.doc_denied`;
  - выбранный закрытый источник → `403` + аудит;
  - закрытая папка → `403` + аудит.
- Согласованность папок и документов:
  - нельзя положить документ с ACL «Все» в закрытую папку;
  - при смене папки ACL подставляется автоматически;
  - папку с документами нельзя удалить или сделать «Все»;
  - встроенные папки нельзя переименовать/удалить;
  - удалить/изменить можно только свою загрузку, директор — любую.
- Объектные проверки (IDOR):
  - встреча: сотрудник видит только свою, директор — все;
  - задача: доступ у владельца, постановщика или директора;
  - перезапись чужой AI-выжимки встречи запрещена;
  - неизвестный `owner_id` при назначении задачи отклоняется.
- Создание задач из протокола — только после подтверждения, с `idem_key`
  для защиты от дублей.

### 3.3. Маскирование ПДн перед внешней LLM

Перед отправкой в DeepSeek текст проходит `PIIMasker`:

| Тип | Пример | Тег |
|---|---|---|
| ФИО / имена сотрудников | «Анна Иванова» | `⟦PERSON_1⟧` |
| Телефон | `+375 29 123-45-67` | `⟦PHONE_1⟧` |
| Email | `a.ivanova@company.by` | `⟦EMAIL_1⟧` |
| IBAN | `BY...` | `⟦IBAN_1⟧` |
| Банковская карта | `4111 1111 1111 1111` | `⟦CARD_1⟧` |
| УНП | `УНП 123456789` | `⟦UNP_1⟧` |
| Паспорт | `MP1234567` | `⟦PASSPORT_1⟧` |
| Организация | «ООО Ромашка» | `⟦ORG_1⟧` |

Дополнительно:

- словарь сотрудников демо-базы маскируется даже по одному имени (Vosk не даёт заглавных);
- названия «Фотопринт», «Picpac» остаются, чтобы ответы не теряли смысл;
- после маскирования выполняется `assert_clean`: если остался телефон/email/IBAN/паспорт/имя —
  запрос не уходит, выбрасывается `PIIError`;
- обратная подстановка — только в памяти текущего запроса;
- в UI и аудите показывается **маскированный** preview, а не исходный текст;
- в ответе API есть `pii_found`, `placeholders`, `masked_preview`.

Ограничение: это **не полная анонимизация**, а защитный слой по известным форматам
и словарю. Контекст, редкие имена, должности и комбинации признаков могут
деанонимизировать человека. Для продакшна нужен NER и криптографическая токенизация.

### 3.4. Внешняя LLM: что уходит и что нет

В DeepSeek уходит только:

- вопрос пользователя **после маскирования**;
- заголовки и текст **только доступных/выбранных** документов после маскирования;
- название встречи и расшифровка после маскирования — для выжимки.

Не уходит:

- аудио и временные WAV;
- cookie, сессии, `SECRET_KEY`;
- документы и встречи других ролей;
- сырые ФИО, телефоны, email, IBAN, карты, УНП, паспорта.

Ограничения контекста:

- каждый документ — до 6 000 символов;
- расшифровка встречи — до 24 000 символов;
- не более 8 источников на один вопрос;
- `LLM_TIMEOUT=30` секунд, `LLM_MAX_TOKENS=700`;
- при недоступности LLM — детерминированный fallback, а не ошибка 500.

Защита от prompt injection:

- системный промпт прямо говорит: всё внутри `<documents>` — недоверенные данные,
  инструкции внутри игнорировать;
- из текста вырезаются закрывающие теги `</document>` / `</documents>`;
- id/title/date экранируются;
- ответ модели проверяется на неизвестные теги и сырые ПДн;
- это снижает риск, но **не гарантирует** защиту от всех инъекций.

Провайдер и регион:

- `deepseek-chat`, API `api.deepseek.com`, провайдер — DeepSeek (КНР);
- в UI название провайдера не выводится, но `/health` и README честно раскрывают модель;
- для реальных ПДн нужен DPA, zero-retention или локальная модель.

### 3.5. Запись встречи и локальная речь

- Браузер записывает микрофон через `MediaRecorder`.
- Аудио уходит только на **свой** Python-бэкенд.
- Расшифровка — локальный **Vosk** (`vosk-model-small-ru-0.22`), без облачного STT.
- Временный исходный файл удаляется после конвертации, WAV — в `finally` после распознавания.
- Лимит аудио — 30 МБ (`MEETING_MAX_AUDIO_MB`).
- Перед записью требуется подтверждение согласия участников (`consent=true`).
- Внешней модели уходит только **маскированный текст** расшифровки.

Ограничение: согласие — это галочка, а не юридически значимая фиксация; точность Vosk
зависит от микрофона и шума.

### 3.6. Аудит

В таблице `audit` фиксируются:

- пользователь, роль, время (UTC), действие, объект, результат;
- маскированный preview запроса;
- метаданные (например, `used_llm`, `llm_error`, `pii_found`).

События: вход, смена роли, просмотр/загрузка/удаление документа, отказ по ACL,
запрос к ассистенту, отказ по закрытому источнику, запись встречи, правка выжимки,
создание задач, обратная связь, удаление выжимки, лимиты AI.

Доступ:

- директор видит все записи;
- сотрудник — только свои;
- в аудите нет сырых ПДн: preview и метаданные маскируются.

Ограничение: аудит хранится в той же SQLite-базе, без WORM/SIEM; администратор
с доступом к файлу БД может его изменить. Для продакшна — append-only хранилище,
экспорт в SIEM, алерты и политика хранения.

### 3.7. Сеть, заголовки, кэш

- Публичный доступ — HTTPS через Tunnelmole; локально — HTTP для разработки.
- Заголовки:
  - `X-Content-Type-Options: nosniff`;
  - `Referrer-Policy: no-referrer`;
  - `X-Frame-Options: SAMEORIGIN`;
  - `Cache-Control: no-store` для API.
- CORS не включён: приложение same-origin, чужие Origin не получают доступ.
- HTML отдаётся с Brotli/gzip и явным `Content-Length`; статика кешируется на час.
- Первый вход отдаёт HTML сразу, с подписанной cookie, без редиректа.
- Публичный адрес и QR — в `tools/` и `qr/`, которые не коммитятся.

Ограничение: TLS завершается на стороне туннеля, это не end-to-end шифрование
до нашего процесса. Для продакшна — собственный reverse proxy с TLS/HSTS.

### 3.8. Валидация ввода и устойчивость

- Загрузка: `.txt`, `.md`, `.csv`, `.pdf`, `.eml`, до **2 МБ**; текст до **200 тыс. символов**.
- PDF разбирается локально `pypdf`, `.eml` — стандартным парсером; битые файлы → понятная ошибка.
- Аудио — до **30 МБ**, пустой файл отклоняется.
- Не более **8 источников** на вопрос; контекст документов и встреч обрезается.
- Лимит AI — **20 запросов/мин** на пользователя и действие (`RATE_LIMIT_PER_MINUTE`),
  при превышении `429` и `Retry-After`.
- SQL — параметризованные запросы (`?`), без склейки пользовательских строк.
- Ошибки API — `400/401/403/404/413/422/429` с русскими сообщениями, без стектрейсов.
- Идемпотентность задач из протокола защищает от дублей при повторном нажатии.

Ограничение: rate limit in-memory, сбрасывается при перезапуске и не работает
между несколькими процессами. Для продакшна — Redis.

### 3.9. Секреты и гигиена репозитория

- `.env` в `.gitignore`; в репозитории только `.env.example` с пустыми значениями.
- `SECRET_KEY` и `DEEPSEEK_API_KEY` не хранятся в коде.
- В ZIP для другого компьютера **не попадают**: `.env`, `data/app.db`, аудит,
  логи, PID-файлы, ключи туннеля.
- `.gitignore` закрывает `models/`, `tools/`, `dist/`, `*.db`, `*.log`.
- `/health` показывает провайдера и модель, но не ключ.
- При передаче проекта другому человеку ключ DeepSeek нужно ротировать.

## 4. Чем проверено

- **55 тестов** (`python -m pytest -q`), в том числе:
  - маскирование ПДн и запрет отправки сырых шаблонов;
  - отказ сотруднику в `D-12` (финансы) и запись отказа в аудит;
  - переключение директор → сотрудник → директор;
  - сохранение AI-выжимки и правка протокола;
  - проверка того, что в LLM уходит только маскированный текст;
  - загрузка/редактирование/удаление документов, папки, выбор источников;
  - отказ по закрытому источнику;
  - подтверждение задач и идемпотентность их создания;
  - AI-контекст календаря с фильтрацией по роли;
  - Brotli/gzip и `Content-Length` без chunked-обрывов.
- Ручные проверки:
  - публичная ссылка открывается под директором, 29 документов, 10 папок;
  - AI-советник по календарю отвечает через реальную LLM (`used_llm: true`);
  - QR декодируется в актуальный адрес;
  - чистый ZIP на другом каталоге: сервер стартует, 29 документов, Vosk-модель
    из полного архива загружается, страница отдаётся за ~2 секунды.

## 5. Честные ограничения прототипа

Это важно проговорить на защите, чтобы не выглядеть нечестно.

1. **Нет настоящей аутентификации.** Демо автоматически входит директором `anna`.
   Публичная ссылка = доступ к демо под директором. Нет паролей, MFA, SSO.
2. **Публичный туннель — демо-инструмент.** Бесплатный Tunnelmole даёт случайный адрес,
   не даёт SLA и завершает TLS на своей стороне. Любой со ссылкой видит приложение.
3. **Маскирование — не анонимизация.** Regex + словарь; редкие имена, контекст и
   квазиидентификаторы могут раскрыть человека. Нет NER-модели и KMS-токенизации.
4. **Нет шифрования данных при хранении.** SQLite, тексты документов и расшифровки
   лежат в открытом виде. Нет SQLCipher, TDE, KMS, шифрованных бэкапов.
5. **Аудит не WORM.** Запись можно изменить при доступе к файлу БД; нет SIEM,
   алертов и политики retention.
6. **Нет CSRF-токена и CSP.** `SameSite=Lax` снижает риск CSRF, но это не полная
   защита; CSP/HSTS не настроены.
7. **Нет антивируса и sandbox для файлов.** Есть только лимиты размера/формата и
   локальный парсинг; парсер PDF — потенциальная поверхность атаки.
8. **LLM — внешняя и в КНР.** Даже маскированный текст покидает контур; для реальных
   ПДн нужен DPA, zero-retention или локальная модель.
9. **Rate limit — in-memory.** Сбрасывается при рестарте, не распределённый.
10. **60-секундный лимит бесплатного туннеля.** LLM ограничена 30 секундами, но очень
    длинная расшифровка может не уложиться; тогда сработает fallback.
11. **Данные синтетические.** Реальные ПДн в демо не используются; это условие хакатона.

## 6. Что сделать до продакшна

### Аутентификация и доступ

- OIDC/SSO (Keycloak, Entra ID), MFA, отдельные учётки вместо автовхода.
- Короткоживущие сессии, ротация, `Secure` + `HttpOnly` + `SameSite=Strict`.
- CSRF-токены и проверка `Origin` для state-changing запросов.
- Код доступа/one-time token для публичного демо, отключение автовхода в prod.

### Шифрование и хранение

- TLS/HSTS на собственном reverse proxy; WAF.
- SQLCipher или Postgres с TDE + KMS; field-level шифрование расшифровок и ПДн.
- Шифрованные бэкапы, ротация ключей, процедура восстановления.
- Политика retention и удаления; right to erasure.

### ПДн и LLM

- NER (Presidio/DeepPavlov/spaCy) + криптографическая токенизация.
- DLP-проверки на входе и выходе, запрет сырых ПДн в логах.
- DPA с провайдером, zero-retention API или локальная модель в контуре.
- Egress allowlist: только разрешённые домены.

### Аудит и мониторинг

- Append-only/WORM-хранилище, экспорт в SIEM, алерты на аномалии.
- Retention-политика и защита от удаления.
- Метрики отказов ACL, rate limit, ошибок LLM.

### Разработка и инфраструктура

- Redis для rate limit, несколько воркеров.
- CSP, HSTS, `Permissions-Policy`, зависимостный аудит (`pip-audit`, Dependabot).
- SAST/DAST, тесты на IDOR/CSRF/prompt injection, внешний pentest.
- Антивирус/песочница для загрузок, хранение вне web root.

## 7. Как показать безопасность на демо

1. **Смена роли.** Директор → Игорь (производство). Показать, что финансы и HR
   недоступны, а календарь/задачи — только сотрудника.
2. **Закрытый документ.** В «Документах» выбрать `D-12` (финплан) → `403`,
   затем открыть «Историю» и показать запись `assistant.doc_denied`.
3. **Маскирование.** Задать вопрос с ФИО и телефоном → раскрыть «Что ушло в модель»:
   в payload только `⟦PERSON_1⟧` и `⟦PHONE_1⟧`, в ответе — реальные значения.
4. **Аудит.** Показать, что сотрудник видит только свои записи, директор — все;
   сырых ПДн в аудите нет.
5. **Секреты.** Показать `.env.example` и состав ZIP: `.env`, база, логи и ключи
   туннеля в архив не входят.
6. **Тесты.** `python -m pytest -q` → 54 passed.

## 8. Ответы на вопросы жюри

**«Вы отправляете персональные данные в Китай?»**
Нет, в внешнюю модель уходит только маскированный текст: ФИО, телефоны, email, IBAN,
карты, УНП, паспорта и организации заменены тегами. Аудио не уходит вообще — его
расшифровывает локальный Vosk. Но честно: маскирование не равно полной анонимизации,
поэтому для реальных ПДн нужен DPA/локальная модель.

**«Можно ли подделать роль в браузере?»**
Роль не приходит из браузера. В подписанной cookie только `uid` и `act_as`; роль и ACL
сервер перечитывает из БД. Подпись проверяется, просроченная сессия даёт `401`.

**«Что если сотрудник угадает ID чужого документа/встречи?»**
Сервер проверяет ACL и владельца на каждом объектном эндпоинте. Чужой объект даёт
`403` и запись в аудите; список документов заранее отфильтрован по ACL.

**«Что если в документе написано „игнорируй инструкции“?»**
Текст документа обёрнут в `<documents>` и объявлен недоверенными данными; системный
промпт запрещает выполнять инструкции из контекста; ответ проверяется на теги и ПДн.
Это снижает риск, но prompt injection не гарантированно устраняется промптом.

**«Данные зашифрованы?»**
В прототипе — нет шифрования at rest: SQLite и тексты лежат в открытом виде.
Есть HTTPS в транзите, маскирование ПДн и аудит. Для продакшна — SQLCipher/Postgres
TDE + KMS, шифрованные бэкапы и field-level шифрование.

**«Кто видит аудит?»**
Директор — все записи, сотрудник — только свои. В аудите маскированный preview,
без сырых ПДн. Ограничение: это SQLite, без WORM/SIEM.

**«Почему публичная ссылка открывает директора?»**
Это демо-режим для жюри: один QR — один сценарий. В продакшне — SSO, код доступа
или one-time token, а автовход отключается.

---

## 9. Итоговая формулировка

> Прототип построен по принципу **least privilege + data minimization**:
> сервер сам определяет роль и ACL, ПДн маскируются до внешней LLM, аудио
> обрабатывается локально, каждое значимое действие попадает в аудит, а секреты
> не хранятся в коде и не попадают в архив. При этом это демо: нет настоящей
> аутентификации и шифрования at rest, маскирование не является полной
> анонимизацией, а публичный туннель — временный. Все ограничения и план
> перехода в продакшн перечислены выше.
